```

  └─ GitHub Actions: 타입 검사 → 테스트 → 브라우저 테스트 → 빌드(운영·스테이징) → 비밀 값 검사 → Pages 배포 → 배포 후 확인
```

## 핵심 결정
1. **규칙 코드 하나** — `shared/` (TypeScript 순수 함수)를 클라이언트는 그대로, GAS 는 `npm run build:gas` 로 묶은 `GameCore.gs` 로 씀. 반올림·큰 수·전투 계산이 양쪽에서 똑같음. CI 가 `GameCore.gs` 가 최신인지 검사
2. **서버 권위** — 클라이언트는 의도(upgrade·setTeam·challengeBoss·claimOffline·rebuildEcology·setAlias)만 보냄. 재화·보상·승패·시각은 서버가 계산
3. **보기 = 예측** — 클라이언트는 마지막 서버 상태를 지금 시각까지 정산한 '보기'를 그려 숫자가 실시간으로 오름. 서버 응답이 오면 그대로 바꿈(더하지 않음)
4. **상태 한 행** — 플레이어 상태는 JSON 한 셀(최대 45KB). 한 번의 setValues 가 확정 지점. 큰 수는 문자열
5. **멱등성** — 모든 요청에 requestId(UUID). 상태 안에 최근 40개 기억 → 응답 유실 후 재전송해도 한 번만 적용
6. **낙관적 동시성** — expectedRevision 이 다르면 VERSION_CONFLICT. 두 탭·두 기기 동시 조작 보호
7. **hash 라우팅** — `#/explore` 등. Pages 에서 새로고침·직접 진입해도 404 없음. 잘못된 경로는 `404.html` 이 첫 화면으로
8. **프레임워크 없음** — 화면 5개 규모라 React 없이 TypeScript + 템플릿 문자열. 번들 59KB(gzip 22KB)
9. **그림 직접 생성** — 공명체·보스·배경은 코드로 그린 SVG (외부 이미지·폰트·아이콘 없음)

## 요청 흐름 (upgrade 예)
1. 화면 버튼 → `session.send('upgrade', {kind:'level', id})` → 큐(IndexedDB)에 저장
2. `fetch(POST, text/plain)` → GAS `doPost` → 크기(16KB)·JSON·모양 검사 → 버전·점검 확인 → 토큰 → 빈도 제한
3. `LockService.tryLock(8초)` → 행 찾기 → 상태 읽기 → `GameCore.processRequest`
   (중복 → 그대로 돌려줌 / revision 확인 / settle(지난 구간 정산) / 비용·소유·해금 검사 / 적용 / revision+1)
4. 상태 한 행 쓰기 → CommandJournal 추가 → 잠금 해제 → `{ok, code, revision, data:{state, result, config}}`
5. 클라이언트: 큐에서 삭제 → 상태 교체 → 다른 탭에 알림(BroadcastChannel)

## 실패 처리
| 상황 | 서버 | 클라이언트 |
|---|---|---|
| 네트워크 끊김 · 시간 초과 | – | 같은 requestId 로 최대 4번 (지수 백오프 0.5→1→2초 + 지터), 실패하면 큐에 두고 온라인 복귀 때 다시 |
| 잠금 대기 초과 | SERVER_ERROR(BUSY), 변화 없음 | 재시도 |
| 상태 저장 후 기록 실패 | 상태의 recent 로 중복 방지, `reconcile()` 이 기록 보충 | – |
| revision 충돌 | VERSION_CONFLICT | 최신 상태 받기, 그 명령은 버리고 안내 |
| 점검 | MAINTENANCE | 점검 화면 |
| 오래된 클라이언트 | INVALID_REQUEST(CLIENT_TOO_OLD) | 새로고침 안내 |
| `beforeunload` | – | 쓰지 않음(보장 안 됨). 대신 10분 자동 저장 + 탭 복귀 시 sync |
